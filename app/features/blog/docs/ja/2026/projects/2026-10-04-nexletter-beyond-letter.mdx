## 最初は週次レポートを考えていた

NexLetterの最初の構想は、比較的シンプルだった。

毎日複数のソースから情報を収集・分析し、**Daily Core Data**を積み上げていく。  
そして1週間分たまったCore Dataを改めて分析し、1つの**Weekly Report**を作る。

当初は、日ごとのCore Dataを、週次レポートの質を高めるための土台となるデータに近いものとして考えていた。

ただ、構造について考え続けるうちに、ひとつ疑問が出てきた。

毎日それなりのコストと手間をかけて良いCore Dataを作っているのに、それを1週間ただ寝かせておく必要は本当にあるのだろうか。

そこで、方向を少し変えることにした。

---

## Core Dataは毎日価値を生み出せる

新しい構造では、Daily Core Dataができた時点で、その日のうちに**Daily Report**も生成する。

そしてその中から最も重要なHighlightを最大3つほど選び、Slackチャンネルに送る。

たとえば、こんな構造だ。

```text
Daily Collection
      ↓
Daily Core Data
      ↓
 ┌────┴─────────┐
 ↓              ↓
Highlights    Daily Report
 ↓              ↓
Slack           Email
```

Slackですべての内容を見せる必要はない。

今日知っておくべき重要な変化をいくつか、短く読みやすい形で見せればいい。

この部分は、Market Memoryを作るときに使っていた**30秒Brief**ともかなり近い。

全体の流れをざっと把握したい人はSlackだけ確認すればいいし、もう少し詳しく見たい人はメールで届いたDaily Reportを読めばいい。

そして1週間が終わったら、月曜日から金曜日までに積み上がったCore Dataを改めて分析する。

```text
Mon Core ┐
Tue Core │
Wed Core ├─→ Weekly Analysis → Weekly Report → Email
Thu Core │
Fri Core ┘
```

ここで大事なのは、Weekly ReportがDaily Reportをまとめ直したものではない、という点だ。

加工済みの文章を要約し直すのではなく、**元データに近いCore Dataをもう一度分析して、1週間の流れを新たに組み立てる。**

Dailyでは見えなかったつながりや、数日にわたって続いた変化も、この過程で改めて見つけることができる。

---

## でも、SlackとEmailである必要はあるのだろうか

ここまで考えたところで、DAMIを作りながら試したことが自然と頭に浮かんだ。

1つのCore Dataがあるなら、それを1つの形だけで消費しなければならない理由はない。

DAMIでは、同じデータをBrief、Voice、Full Report、Chatなど、いくつかの方法で消費できるようにした。

NexLetterでも、同じアプローチが取れる。

```text
                 ┌─ Slack Brief
                 │
Daily Core Data ─┼─ Daily Report → Email
                 │
                 ├─ Voice Briefing
                 │
                 └─ Chat
```

通勤中にVoiceで今日の主な内容を聞くこともできるし、仕事中はSlackでHighlightだけをさっと確認することもできる。

もう少し詳しく見たければ、Daily Reportを読む。

そして気になることが出てきたら、Chatで直接質問する。

Cloudflare Workersなどを使えば、DAMIで作ったものと似たWebベースのChatインターフェースを組み込むことも十分に可能だ。

ここまで来ると、Emailはサービスそのものではなく、いくつかある届け方のひとつになる。

---

## Chatが加わると、話が少し変わってくる

最初は、Chatについても、生成されたレポートに質問できる機能くらいに思えるかもしれない。

ただ、NexLetterがSlackとつながっているなら、もっと面白いことができる。

チームでは毎日、Slackでたくさんの業務の話をしている。

今何をしているかを共有し、問題が起きればそれを報告し、解決方法を議論する。作業が終われば、結果や成果も残す。

これが数か月分たまると、かなりの量の業務記録になる。

問題は、記録は残っていても、時間が経つとあとから探し出すのが簡単ではないということだ。

たとえば、新しい業務を始めるときに、こんな質問をするかもしれない。

> 今やっているXXXの業務と似た作業を、以前やったことはあっただろうか？

単なるキーワード検索ではなく、過去の業務の文脈まで見つけ出せるなら、話は違ってくる。

> 4月に進めたYYYの業務が、現在の作業と似ています。  
> 当時は最初にAの方法で進めましたが、Bの問題が発生し、その後Cの方法に変更しました。

そして、さらに質問を続けられる。

> そのときの問題は何だった？

> どれくらいかかった？

> 最終的にどうやって解決した？

> 当時のSlackの会話を見せて。

> そのときと今の状況を比較して。

こうした機能が実現できれば、Chatは単にレポートに質問するためのインターフェースではなくなる。

**チームが過去に何をしてきたのかを、もう一度取り出せるインターフェース**になる。

---

## 毎日のCore Dataがチームの記憶になる

そう考えると、Daily Core Dataの意味もまた変わってくる。

ニュースや外部の情報を整理するだけでなく、必要であればSlackで生まれた業務の流れも構造化できる。

```text
Slack Conversations
        ↓
Daily Analysis
        ↓
Daily Work Core
        ↓
 ┌────────────────────┐
 │ 主な業務           │
 │ 決定事項           │
 │ 進捗状況           │
 │ 問題と解決         │
 │ 成果               │
 │ 関連プロジェクト   │
 │ 元のSlack Message  │
 └────────────────────┘
        ↓
Long-term Memory
        ↓
Chat
```

毎日Briefingを作ることが、そのまま**チームの業務の記憶を整理する作業**にもなるわけだ。

すると、サービスには2つの時間軸が生まれる。

1つは**現在**だ。

今日何が重要だったかを整理して、Slack、Email、Voiceなどで届ける。

もう1つは**過去**だ。

積み重ねてきたCore Dataと元データをもとに、過去の決定や業務の流れをChatを通じて改めて見つけ出す。

結局、

> 今日何が重要かを教えてくれて、  
> 自分たちが過去に何をしてきたかも覚えていてくれるAgent。

という方向まで考えることができる。

---

## では、NexLetterという名前は今も合っているのだろうか

ここまで考えたところで、新しい悩みが出てきた。

**NexLetterという名前は、いま作ろうとしているものを、まだうまく表せているだろうか。**

最初はかなり合っていた。

Weekly Reportを生成してEmailで届けるサービスだったからだ。

文字どおり、少し進化した形のNewsletterを考えていた。

でも今、Emailはいくつかある出力方法のひとつにすぎない。

```text
Collect
   ↓
Understand
   ↓
Structure
   ↓
 ┌───────────────┐
Slack   Email   Voice
   └──────┬────────┘
          ↓
        Chat
          ↕
       Memory
```

重要な情報を見つけ出し、構造化し、必要な形で届ける。

そしてユーザーが質問すれば、積み重なった記憶の中から関連する文脈を見つけてくれる。

これを単に`Letter`と呼ぶには、サービスの範囲がだいぶ広がってしまった。

Briefing Agentに近いのかもしれないし、チームのSignalを見つけてくれるAgentなのかもしれない。

さらに言えば、組織のContextやMemoryを蓄積するAgentと見ることもできる。

まだ新しい名前を決めたわけではない。

むしろ今は、名前を先に決めるよりも、**このサービスが何になりつつあるのかをもう少しはっきりさせることが先**だと考えている。

---

## Letterから始まったけれど

最初からこういうサービスを作ろうとしていたわけではない。

週次レポートをもう少しうまく作りたくて、そのためにDaily Core Dataを積み上げようとしていた。

でも、Daily Core Dataを作るならDaily Reportも作れたし、重要な部分だけを抜き出せばSlack Briefになった。

同じデータをVoiceに変えることもできたし、Chatを付ければ質問もできた。

そしてSlackにたまり続ける業務記録までつなげて考えてみると、単なるレポート生成ツールにとどまらず、**チームの記憶を蓄積し、あとから取り出せる機能**まで見えてきた。

だから今のNexLetterは、最初に考えていたNexLetterとは少し違うものになっている。

名前まで変わることになるかは、まだわからない。

ただ、ひとつははっきりした。

**今、自分が作りたいのは、単にLetterをうまく作ってくれるサービスだけではない。**

毎日重要なことを見つけて知らせてくれて、時間が経てばその記録がやがてチームの記憶になっていくもの。

今は、その方向のほうが少し面白く思える。
