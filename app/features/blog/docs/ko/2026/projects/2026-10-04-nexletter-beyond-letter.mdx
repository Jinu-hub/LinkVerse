## 처음에는 주간 리포트를 생각했다

NexLetter의 초기 구상은 비교적 단순했다.

매일 여러 소스에서 정보를 수집하고 분석해 **Daily Core Data**를 쌓는다.  
그리고 일주일 동안 축적된 Core Data를 다시 분석해 하나의 **Weekly Report**를 만든다.

처음에는 일별 Core Data를 주간 리포트의 품질을 높이기 위한 기반 데이터에 가깝게 생각했다.

하지만 구조를 계속 생각하다 보니 한 가지 의문이 생겼다.

매일 꽤 많은 비용과 과정을 거쳐 좋은 Core Data를 만들고 있는데, 굳이 그것을 일주일 동안 저장만 해둘 필요가 있을까?

그래서 방향을 조금 바꾸기로 했다.

---

## Core Data는 매일 가치를 만들 수 있다

새로운 구조에서는 Daily Core Data가 만들어지면 그날 바로 **Daily Report**도 생성한다.

그리고 그중 가장 중요한 Highlight를 최대 3개 정도 뽑아 Slack 채널에 전달한다.

예를 들면 이런 구조다.

```text
Daily Collection
      ↓
Daily Core Data
      ↓
 ┌────┴─────────┐
 ↓              ↓
Highlights    Daily Report
 ↓              ↓
Slack           Email
```

Slack에서는 모든 내용을 보여줄 필요가 없다.

오늘 알아야 할 중요한 변화 몇 가지만 짧고 읽기 좋게 보여준다.

이 부분은 Market Memory를 만들면서 사용했던 **30초 Brief**와도 상당히 비슷하다.

빠르게 전체 흐름을 파악하고 싶은 사람은 Slack만 확인하면 되고, 조금 더 자세히 보고 싶은 사람은 이메일로 전달된 Daily Report를 읽으면 된다.

그리고 한 주가 끝나면 월요일부터 금요일까지 축적된 Core Data를 다시 분석한다.

```text
Mon Core ┐
Tue Core │
Wed Core ├─→ Weekly Analysis → Weekly Report → Email
Thu Core │
Fri Core ┘
```

여기서 중요한 것은 Weekly Report가 Daily Report를 다시 요약하는 구조가 아니라는 점이다.

가공된 글을 다시 요약하기보다 **원본에 가까운 Core Data를 다시 분석해서 한 주의 흐름을 새롭게 구성한다.**

Daily에서는 보이지 않았던 연결 관계나 며칠 동안 이어진 변화도 이 과정에서 다시 발견할 수 있다.

---

## 그런데 꼭 Slack과 Email이어야 할까?

여기까지 생각하고 나니 DAMI를 만들면서 했던 실험이 자연스럽게 떠올랐다.

하나의 Core Data가 있다면 그것을 꼭 하나의 형태로만 소비할 이유가 없다.

DAMI에서는 같은 데이터를 Brief, Voice, Full Report, Chat 등 여러 방식으로 소비할 수 있도록 만들었다.

NexLetter에서도 같은 접근이 가능하다.

```text
                 ┌─ Slack Brief
                 │
Daily Core Data ─┼─ Daily Report → Email
                 │
                 ├─ Voice Briefing
                 │
                 └─ Chat
```

출근하면서 Voice로 오늘의 주요 내용을 들을 수도 있고, 업무 중에는 Slack에서 Highlight만 빠르게 확인할 수도 있다.

조금 더 자세히 보고 싶다면 Daily Report를 읽는다.

그리고 궁금한 것이 생기면 Chat에서 직접 질문한다.

Cloudflare Workers 등을 활용하면 DAMI에서 만들었던 것과 비슷한 웹 기반 Chat 인터페이스를 붙이는 것도 충분히 가능하다.

여기까지 오면 Email은 서비스 자체가 아니라 여러 전달 방식 중 하나가 된다.

---

## Chat이 붙으면 이야기가 조금 달라진다

처음에는 Chat 역시 만들어진 리포트에 질문할 수 있는 기능 정도로 생각할 수 있다.

하지만 NexLetter가 Slack과 연결되어 있다면 훨씬 재미있는 것이 가능하다.

팀에서는 매일 Slack을 통해 많은 업무 이야기를 한다.

현재 무엇을 하고 있는지 공유하고, 문제가 발생하면 이야기하고, 해결 방법을 논의한다. 작업이 끝나면 결과나 성과도 남긴다.

이것들이 몇 달 동안 쌓이면 상당한 양의 업무 기록이 된다.

문제는 기록은 남아 있지만 시간이 지나면 다시 찾아내기가 쉽지 않다는 것이다.

예를 들어 새로운 업무를 시작하면서 이런 질문을 할 수 있다.

> 지금 하고 있는 XXX 업무와 비슷한 작업을 예전에 한 적이 있었나?

단순한 키워드 검색이 아니라 과거의 업무 맥락을 찾아낼 수 있다면 이야기가 달라진다.

> 4월에 진행했던 YYY 업무가 현재 작업과 비슷합니다.  
> 당시에는 처음에 A 방식으로 진행했지만 B 문제가 발생했고, 이후 C 방식으로 변경했습니다.

그리고 다시 질문할 수 있다.

> 그때 문제가 뭐였지?

> 얼마나 걸렸어?

> 최종적으로 어떤 방식으로 해결했어?

> 당시 Slack 대화를 보여줘.

> 그때와 지금 상황을 비교해줘.

이런 기능이 가능해지면 Chat은 단순히 리포트에 질문하는 인터페이스가 아니다.

**팀이 과거에 무엇을 했는지를 다시 꺼내볼 수 있는 인터페이스**가 된다.

## 매일의 Core Data가 팀의 기억이 된다

이렇게 생각하면 Daily Core Data의 의미도 다시 달라진다.

뉴스나 외부 정보를 정리하는 것뿐 아니라 필요하다면 Slack에서 발생한 업무 흐름도 구조화할 수 있다.

```text
Slack Conversations
        ↓
Daily Analysis
        ↓
Daily Work Core
        ↓
 ┌────────────────────┐
 │ 주요 업무          │
 │ 결정 사항          │
 │ 진행 상황          │
 │ 문제와 해결        │
 │ 성과               │
 │ 관련 프로젝트      │
 │ 원본 Slack Message │
 └────────────────────┘
        ↓
Long-term Memory
        ↓
Chat
```

매일 Briefing을 만드는 과정이 동시에 **팀의 업무 기억을 정리하는 과정**이 되는 셈이다.

그러면 서비스에는 두 가지 시간축이 생긴다.

하나는 **현재**다.

오늘 무엇이 중요했는지 정리해서 Slack, Email, Voice 등으로 전달한다.

다른 하나는 **과거**다.

계속 축적된 Core Data와 원본 데이터를 바탕으로 과거의 결정과 업무 흐름을 Chat을 통해 다시 찾아낸다.

결국,

> 오늘 무엇이 중요한지 알려주고,  
> 우리가 과거에 무엇을 했는지도 기억해주는 Agent.

라는 방향까지 생각해볼 수 있다.

## 그러면 NexLetter라는 이름은 여전히 맞을까?

여기까지 생각하고 나니 새로운 고민이 생겼다.

**NexLetter라는 이름이 지금 만들려는 것을 여전히 잘 설명하고 있는가?**

처음에는 꽤 잘 맞았다.

Weekly Report를 생성해서 Email로 전달하는 서비스였기 때문이다.

말 그대로 조금 더 발전된 형태의 Newsletter를 생각했다.

하지만 지금 Email은 여러 출력 방식 중 하나일 뿐이다.

```text
Collect
   ↓
Understand
   ↓
Structure
   ↓
 ┌───────────────┐
Slack   Email   Voice
   └──────┬────────┘
          ↓
        Chat
          ↕
       Memory
```

중요한 정보를 찾아내고, 구조화하고, 필요한 방식으로 전달한다.

그리고 사용자가 다시 질문하면 축적된 기억에서 관련된 맥락을 찾아준다.

이것을 단순히 `Letter`라고 부르기에는 서비스의 범위가 많이 넓어졌다.

Briefing Agent에 가까울 수도 있고, 팀의 Signal을 찾아주는 Agent일 수도 있다.

더 나아가면 조직의 Context나 Memory를 축적하는 Agent라고 볼 수도 있다.

아직 새로운 이름을 정한 것은 아니다.

오히려 지금은 이름을 먼저 정하기보다 **이 서비스가 무엇이 되어가고 있는지를 조금 더 명확하게 만드는 것이 먼저**라고 생각한다.

## Letter에서 시작했지만

처음부터 이런 서비스를 만들려고 했던 것은 아니다.

주간 리포트를 조금 더 잘 만들어보려 했고, 그러기 위해 Daily Core Data를 쌓으려고 했다.

그런데 Daily Core Data를 만들 거라면 Daily Report도 만들 수 있었고, 중요한 부분만 뽑으면 Slack Brief가 되었다.

같은 데이터를 Voice로 바꿀 수도 있었고, Chat을 붙이면 질문할 수도 있었다.

그리고 Slack에 계속 쌓이는 업무 기록까지 연결해서 생각하니, 단순한 리포트 생성기를 넘어 **팀의 기억을 축적하고 다시 꺼내는 기능**까지 보이기 시작했다.

그래서 지금의 NexLetter는 처음 생각했던 NexLetter와 조금 달라졌다.

이름까지 바뀌게 될지는 아직 모르겠다.

다만 한 가지는 분명해졌다.

**이제 내가 만들고 싶은 것은 단순히 Letter를 잘 만들어주는 서비스만은 아니다.**

매일 중요한 것을 찾아서 알려주고, 시간이 지나면 그 기록이 다시 팀의 기억이 되는 것.

지금은 그 방향이 조금 더 재미있어 보인다.
